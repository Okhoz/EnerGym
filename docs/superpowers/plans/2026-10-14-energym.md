# EnerGym Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Entregar un MVP Android Java/XML con rutinas compatibles, registro local, asistente OpenAI mediante backend y recursos visuales de internet con disponibilidad honesta.

**Architecture:** Dominio Java independiente de Android, repositorios SQLite y pantallas XML. Backend Java separado valida propuestas y consulta Responses API. Un registro de recursos visuales limita los comandos a las capacidades reales de cada recurso.

**Tech Stack:** Java 11 en Android, AndroidX/Material existentes, SQLiteOpenHelper, Java 17 y Maven para backend, HTTPS/JSON y Responses API con Structured Outputs. No se introduce Kotlin en el código Android.

**Spec:** ../specs/2026-10-14-energym-design.md

## Global Constraints

- Comentarios/Javadoc útiles en español para contratos públicos, MVC, privacidad y decisiones no obvias; revisión final de comentarios del modelo ya creado.

- MVC explícito por instrucción del usuario: modelo en domain/catalog/data; vistas XML y actividades/fragmentos; coordinación en controller/. Vistas sin reglas de negocio ni SQL.

- Proyecto: `C:\Users\oscar\AndroidStudioProjects\EnerGym`, paquete `com.energym.app`, minSdk 26, configuración actual compileSdk/targetSdk 37.
- Interfaces XML y código de aplicación Android Java; conservar Gradle Kotlin DSL.
- Almacenamiento local por usuario y sincronización Firestore; acceso mediante cuenta Google. Ampliación explícita del usuario sustituye la exclusión original de sincronización.
- Clave OpenAI únicamente en servidor; no simular respuestas del proveedor.
- Sin material no presupone silla, pared ni apoyo.
- Cambios de rutina solo después de aceptar una vista previa.
- Recursos de internet con licencia documentada y revisión por ejercicio; sin compras autorizadas.
- La demostración es referencia, no evaluación personal; no hay análisis por cámara.

## Review Focus

1. Recreación de actividad durante una sesión: conservar borrador y evitar doble guardado (tareas 3–4).
2. Cambio de equipo después de una propuesta: revalidar antes de aceptar (tareas 2 y 6).
3. Respuesta tardía del chat tras cambiar de ejercicio: conservar el contexto original y no controlar el recurso nuevo (tarea 6).
4. Accesorio implícito en un ejercicio catalogado como peso corporal: requisitos explícitos prevalecen sobre su categoría (tarea 2).
5. Recurso visual corrupto, incompatible o sin licencia clara: fallback visible sin anunciar capacidades inexistentes (tarea 7).
